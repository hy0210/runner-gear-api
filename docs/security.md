# 資安檢查清單與紀錄

## 流程上的檢查
| 時機 | 檢查 |
|---|---|
| 寫 spec | issue 必填「安全考量」，否則不得標 `spec:ready` |
| 每次 push / PR（CI） | gitleaks、`npm audit --audit-level=high`、eslint-plugin-security |
| GitHub 內建 | Secret scanning、push protection、Dependabot alerts、CodeQL（由使用者開啟） |
| 每個批次 PR 送審前 | 另一個 agent session 做獨立資安審查，結果記在本文件與 PR 留言 |
| 繳交前 | 線上實測：無 Token 打購物車得 401、會員打管理員 API 得 403、註冊帶 role 無效、回應不含密碼雜湊 |

## 應用程式安全需求
- 密碼以 bcrypt 雜湊；登入失敗訊息不透露是帳號還是密碼錯誤；任何回應都不含密碼欄位。
- JWT 有期限，密鑰為足夠長的隨機字串，只存在環境變數。
- 所有寫入 API 以白名單取欄位，使用者無法自行帶入 `role`、`userId` 等欄位。
- 購物車一律以 Token 內的使用者身分查詢，不接受請求指定使用者。
- 查詢一律用 TypeORM 參數化，不拼接 SQL 字串。
- helmet、CORS 僅允許前端網域、請求大小上限；正式環境錯誤回應不帶 stack trace。
- 限流分三層，都以來源位址計數：`/api/v1` 全站每分鐘 300 次；註冊 15 分鐘 20 次；登入 15 分鐘內失敗 20 次或總計 60 次（成功也算）。上限寫成常數，不由請求或環境變數放寬；登入的限流排在輸入驗證與密碼比對之前。
- 回應一律明確挑選欄位，不直接回傳 entity 或 `save()` 的結果（`save()` 的回傳值仍帶有 `password`）。
- email 一律轉小寫後再儲存與比對，避免大小寫不同造成重複帳號。
- validator 一律用 `z.object`（預設丟棄未知欄位），不用 `looseObject`、`passthrough`；數值欄位要設上限。
- 伺服器記錄不印整個錯誤物件（資料庫錯誤會帶 SQL 參數）。
- `.env` 不進版本庫；agent 不讀寫 `.env`。

## 已知風險
- 需求規定 README 要公開管理員測試帳號，任何人都能刪改商品。對策：seed 可重複執行還原資料；審核期間每天檢查一次商品資料。

- 管理員測試帳號的密碼若外洩或被改，重跑 `npm run seed:admin` 可重設密碼，但**已簽發的 Token 在到期前仍有效**（沒有撤銷機制）。緊急時更換 `JWT_SECRET` 並重啟服務，讓全部 Token 失效。
- 所有限流都以來源位址計數、存在行程記憶體：沒有「每個帳號」的失敗上限，容器重啟後計數歸零；來自大量不同位址的請求不會被擋下（未啟用 CloudFront WAF）。專題規模下接受。
- 測試帳號公開，任何人都能用正確帳密登入。登入總次數上限（15 分鐘 60 次）限制了單一來源能觸發的密碼比對次數；同一個出口位址的多位使用者共用這個額度。
- 限流取得的用戶端位址，前提是 EC2 只接受 CloudFront 連入（安全群組來源為 CloudFront 的 managed prefix list）且 `TRUST_PROXY` 維持 1；若 80 埠對外開放，可用偽造的 `X-Forwarded-For` 繞過限流。部署時需確認。

- 管理員帳號公開，因此商品的名稱、描述、圖片網址可能被寫入任意內容（含 HTML 標籤）。API 只驗證長度與圖片網址的協定（http／https），**前端必須以文字方式輸出**：商品文字用 `{{ }}`、圖片用 `:src` 綁定，不使用 `v-html`，也不把這些值拼進 HTML 或 CSS 字串。
- 管理員的商品寫入 API 沒有數量上限，持有公開帳號的人可以灌入或刪光商品；以 `npm run seed` 還原。
